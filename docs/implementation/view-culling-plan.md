# 視界による配信の絞り込み 実装計画（M1-23）

> **Status**: 実装済み — 2026-10-01（散らした 500 体で 20 TPS・切断 0。全員が同じ場所の cluster は変わらず、100〜150 体が壁）

要件: REQ-ENT-002（視界）、REQ-PERF-001（500 体で 20 TPS）。決定: D6・D13（[decisions.md](../decisions.md)）。
`World` の配信の経路（位置・スニーク・出現と消滅・ブロック変更）を、視界の中だけに絞る。複数の機能にまたがるので、ここに設計を置く。

## 調べたこと

配信の経路は 7 か所（`world.rs`）。いまはどれも全員に送る。

| 経路 | いま | この単位 |
|---|---|---|
| 位置・向き（`EntityPositionSync` + `RotateHead`） | 本人以外の全員 | **視界の中だけ** |
| スニーク（`SetEntityFlagsAndPose`） | 本人以外の全員 | **視界の中だけ** |
| 出現（`AddEntity`）・消滅（`RemoveEntities`） | 入室・退出で全員 | **視界に入る・出るたび、その相手だけ** |
| ブロック変更（`BlockUpdate`、`set_block`） | 全員 | **そのチャンクを持つ（視界にある）プレイヤーだけ** |
| タブリスト（`PlayerInfoAdd` / `Remove`） | 全員 | 全員のまま（視界に関係しない。出現より先に届く必要がある） |
| チャット・サーバーメッセージ・入退室の通知 | 全員 | 全員のまま（視界の話ではない。範囲は v0.2 の Audience） |

M1-18 の計測で、100〜150 体で出力のキューが溢れて切られる原因は、全員への移動の配信が O(N²) なことだと分かっている（[bench-plan.md](bench-plan.md)）。

## 設計

### 視界の定義

- エンティティの視界は、チャンクの正方形: 二人のチャンクの `distance`（大きいほうの軸の差）が `World::entity_view_distance` 以下なら互いに見える。関係は対称
- `World::entity_view_distance`（公開、既定 5。Minestom の既定と同じ）。実際に使う値は `min(entity_view_distance, view_distance)`（チャンクが無い場所のエンティティは見せない）
- ブロック変更は、チャンクの視界（`view_distance`）を使う。クライアントがそのチャンクを持つ範囲と同じ

### 状態

- プレイヤーごとに `visible: HashSet<Uuid>`（いま自分に見えているプレイヤー = 自分を見ているプレイヤー）。移動・スニークの配信はこの集合に送る。全員を走査しない
- 視界の再計算は**チャンクの境界をまたいだときだけ**（全プレイヤーを 1 回走査）。位置が変わっても同じチャンクの中なら何もしない

### 流れ

- **入室**: タブリストは今までどおり（新しい人へ全員分、全員へ新しい人）。そのあと、視界にいる相手とだけ互いに `AddEntity` を送る。出現の順は、**タブリストのあと**（クライアントはタブにいない人を出現させられない）
- **境界をまたぐ**: 移動の配信は古い視界へ、そのあとで視界を再計算する。入ってきた相手とは互いに `AddEntity`、出ていった相手とは互いに `RemoveEntities`
- **出現のとき**: 相手がスニーク中なら、そのフラグと姿勢も送る（視界に入るたびに出現するので、立ったままに見えるのを防ぐ。M1-13 で外した「入室時の `SetEntityData`」はこれで解消する）
- **退出**: 視界にいた相手へ `RemoveEntities`、全員へ `PlayerInfoRemove`
- **ブロック変更**: `set_block` が、そのチャンクが視界に入っているプレイヤーだけに送る

### 計測の道具

- ボットに `--layout cluster|spread`。cluster は今まで（全員がスポーンの近く。最悪のケースで、ベースラインと比べられる）。spread は、全員を互いの視界の外へ格子状に散らす（間隔は `entity_view_distance` + 1 チャンク）
- `xtask bench` に `--layout` と `--view-distance`。lobby は環境変数 `LOBBY_VIEW_DISTANCE` で `view_distance` を変えられる（計測のためだけ）。散らばった 500 人がそれぞれ別のチャンクを持つと、チャンクを破棄しない（M1-15 の ponytail）ためメモリが膨らむので、spread は `--view-distance 2` で測る

## v0.1 でやらなかったこと（後で対応する）

| 項目 | 今の動き | なぜ外したか | 受け皿 |
|---|---|---|---|
| 境界でのヒステリシス | 境界を行き来するたびに出現・消滅を送る | まず絞り込みの効果を取る。チャンク単位で、再計算は境界をまたいだときだけ | 計測で問題になったら |
| 円形の距離・ブロック単位の視界 | チャンクの正方形 | 既存のチャンク送信と同じ単位で、実装が小さい | v0.2 以降 |
| 位置の相対移動（`MoveEntity*`）や、tick ごとの更新のまとめ | 毎回 `EntityPositionSync` と `RotateHead` | 絞り込みとは別の帯域の話 | cluster の壁が残る場合 |
| 視界の範囲を使った配信先（チャット・サウンドなど） | チャットは全員 | Audience（REQ-TEXT-003） | v0.2 |
| 実行中の `view_distance` / `entity_view_distance` の変更 | 入室前に決める。実行中の変更は視界の集合に反映しない | 設定の面は要るものから足す | 必要になったら |
| 全プレイヤー合計の 1 tick のチャンク上限 | プレイヤーごとの予算だけ。spread は別々のチャンクを一斉に要るので N × 予算 | M1-21 から持ち越し。spread の計測は view distance 2 で逃げる | backlog のまま |
| 同じ場所に全員がいる（cluster）ときの O(N²) | 変わらない | 全員が互いに見えているので、絞り込みでは減らない | 上の相対移動・まとめ、`OUTBOX` の見直し |

## テスト

ハーネス（`tests/world.rs`、`view_distance = 2`、`entity_view_distance = 2`）で:

- 遠いプレイヤー（チャンクを 3 以上離れる）には、位置・スニークが届かない。近いプレイヤーには届く
- 遠くへ離れると相手に `RemoveEntities`、戻ると `AddEntity`（そのときの位置）。タブリストは変わらない
- スニーク中の相手が視界に入ったとき、`AddEntity` のあとにフラグと姿勢が届く
- 遠いところへ入室した新しい人（スポーンに入る）は、遠い相手のタブは受けるが `AddEntity` は受けない。遠い相手も新しい人の `AddEntity` を受けない
- 退出: 視界にいた相手は `RemoveEntities` と `PlayerInfoRemove`、遠い相手は `PlayerInfoRemove` だけ
- ブロック変更: 遠いプレイヤーには `BlockUpdate` が届かず、近いプレイヤーには届く。チャットは遠くにも届く
- 既存のテスト（全員が近い）はそのまま通る
- ボット: `--layout spread` の位置が互いの視界の外になる（格子の計算の単体テスト）。統合テスト（`tests/bot.rs`）は、2 体を離して、位置が届かないことを実サーバーで確かめる

## 結果

2026-10-01、Apple M4 Pro（12 コア）、release、ボットは同じマシン、窓 10 秒（cluster は 8 秒）。

**spread**（`cargo xtask bench --layout spread --view-distance 2`。ボットは互いの視界の外に散らす）

| bots | connected | failed | cut off | TPS | avg tick ms | max tick ms | late | skipped | RSS MB |
|---|---|---|---|---|---|---|---|---|---|
| 100 | 100 | 0 | 0 | 20.0 | 0.32 | 278.2 | 0 | 0 | 373.5 |
| 250 | 250 | 0 | 0 | 20.0 | 1.76 | 307.3 | 0 | 0 | 797.6 |
| 500 | 500 | 0 | 0 | 20.0 | 4.57 | 286.0 | 0 | 0 | 1508.5 |

**cluster**（全員がスポーン。絞り込みの対象外）。同じ条件の M1-22 のあと（左）と、この単位のあと（右）の、窓の中で切られた数と平均 tick:

| bots | M1-22 のあと | この単位のあと |
|---|---|---|
| 75 | 切断 0、5.96 ms | 切断 0、6.62 ms |
| 100 | 切断 10、8.41 ms | 切断 0（窓のあとの 2 秒で 47 体が失敗）、9.56 ms |
| 150 | 切断 62、10.32 ms | 切断 6、18.89 ms |

### 読み取れること

1. **視界で絞ると、散らばった 500 体が 20 TPS で、誰も切られない**。要件の「ボット 500 体の接続・移動で 20 TPS」は、散らばった場合に達成した（1 tick の平均 4.6 ms）
2. **全員が同じ場所（cluster）は変わらない**。全員が互いに見えているので、絞り込みでは減らない。100〜150 体が壁のまま。100 と 150 の前後の差は、境目で揺れが大きく、効果ではない（同じ条件で実行ごとにばらつく）
3. **spread の最大 tick が 280〜310 ms**。入室の瞬間（ボットが散らばる位置へ移り、新しいチャンクを大量に要る）を含む。late と skipped は 0。全プレイヤー合計の 1 tick のチャンク上限（M1-21 から持ち越し）が効く場所
4. **RSS はチャンクの数に比例**。500 体で 1.5 GB。チャンクを破棄しないため（M1-15 の ponytail）、散らばるほどメモリが増える
