# 性能ベースライン 実装計画（M1-18）

> **Status**: 実装済み — 2026-10-01（`cargo xtask bench` の結果は下。同条件の Minestom との比較は未実施）

要件: REQ-PERF-001（暫定値の見直し）。決定: D12・D15（[decisions.md](../decisions.md)）。
本体に tick の統計を足し、`xtask bench` で起動時間・アイドル RSS・ボット N 体での tick を表にする。結果をこの文書に残す。

## 測るもの

| 指標 | どう測るか | REQ-PERF-001 の暫定値 |
|---|---|---|
| 起動からリッスン開始まで | `xtask bench` が lobby のプロセスを起動し、TCP 接続が通るまでを 1ms 刻みで待つ。プロセスの起動を含む | < 100ms |
| アイドル RSS | プレイヤー 0 のまま 2 秒待ち、`ps -o rss=` で読む（macOS・Linux 共通） | < 30MB |
| ボット N 体での TPS | サーバーが数える tick の数を、1 秒ごとの出力から、窓（ボットが全員入ったあと）の始めと終わりの差で割る | 500 体で 20 TPS |
| 1 tick の処理時間（平均・最大）、遅れた tick の数 | サーバーの tick 統計（下） | — |
| N 体のときの RSS | 窓の終わりで `ps` | — |

N は 1・10・50・75・100・250・500（75 は、崩れ始める境目を見るために足した）。500 で崩れたら崩れたまま表にする（崩れ方が基準値になる。視界による絞り込みは REQ-ENT-002）。

## 設計

### tick の統計（本体）

`Runner::run` が 1 tick の処理（`step`）にかかった時間を測り、`InstanceHandle::tick_stats()` で読めるようにする。値は起動からの累計。

- `TickStats { ticks, busy, busy_max, late, skipped }`: tick の数、処理時間の合計と最大、予定より 1 tick 以上遅れて始まった tick の数、`MAX_BEHIND` を超えて追いつくのを諦めた回数
- 時計は `Clock::now()` を使う（D21: 実時間を直接読まない）。テストのハーネス（`step` を手で回す）は測らない
- 更新は atomic。`RunningServer::tick_stats()` で取れる

### lobby の統計出力

環境変数 `LOBBY_STATS` があるとき、lobby が 1 秒ごとに 1 行を標準出力へ出す。`xtask bench` が読む。

```
tick-stats ticks=100 busy_us=1234 busy_max_us=900 late=0 skipped=0
```

計測のためだけの出力で、普段は出さない。ログ（tracing）ではなく `println!` にして、色や書式に依存せず読める形にする。

### `xtask bench`

```
cargo xtask bench [--counts 1,10,50,75,100,250,500] [--window 10] [--port 25590]
```

1. `cargo build --release -p lobby -p lodeframe-bot`
2. 起動時間とアイドル RSS: lobby を起動し、接続できるまでの時間と、2 秒後の RSS を取る。3 回やって最小値を表に出す（最初の 1 回はディスクキャッシュの影響が出るため）
3. N ごとに: lobby を**新しく**起動する（キャッシュと前の回の状態を持ち越さない）。ボットの bin に `--count N --seconds (入室の間隔 + 窓)` を渡し、全員が入るまでの待ち（`N × 20ms + 2s`）のあと、`--window` 秒を窓にする。窓の始めと終わりの `tick-stats` から TPS・平均・最大・遅れ・諦めを出し、窓の終わりに RSS を取る
4. 表（Markdown）と、マシン（OS・CPU 数）を標準出力へ出す。プロセスは最後に確実に止める
   - 表の「failed」はボットが切られた数、「cut off」はサーバーが送れずにプレイヤーを切った数（窓の終わりまでのもの）。**この 2 つが 0 でない行の TPS は意味が無い**（切られて空になったサーバーの値）。lobby のログは「送れない」と「もう居ない」を同じ文言で出すので、ボットが抜けたあとの分は数えない

xtask は lobby とボットを**別プロセス**で起動する（RSS をサーバーだけで測るため）。xtask 自体は本体に依存しない（D26 のとおり軽いまま）。

## 結果

2026-10-01、Apple M4 Pro（12 コア、macOS）、release、ボットは同じマシン、窓 10 秒、`cargo xtask bench`。

```
start to listening: 3 ms; idle memory: 3.1 MB
```

| bots | connected | failed | cut off | TPS | avg tick ms | max tick ms | late | skipped | RSS MB |
|---|---|---|---|---|---|---|---|---|---|
| 1 | 1 | 0 | 0 | 20.0 | 0.16 | 45.7 | 0 | 0 | 122.6 |
| 10 | 10 | 0 | 0 | 20.0 | 0.24 | 40.6 | 0 | 0 | 159.0 |
| 50 | 50 | 0 | 0 | 19.9 | 0.99 | 35.3 | 0 | 0 | 340.9 |
| 75 | 75 | 0 | 0 | 20.0 | 1.53 | 36.7 | 0 | 0 | 536.3 |
| 100 | 100 | 99 | 99 | (19.9) | (0.02) | 44.9 | 0 | 0 | 482.7 |
| 250 | 250 | 231 | 231 | (20.0) | (0.62) | 64.6 | 0 | 0 | 627.6 |
| 500 | 500 | 499 | 424 | (20.0) | (0.00) | 61.9 | 0 | 0 | 759.9 |

括弧の TPS は、ほぼ全員が切られたあとの値で、意味が無い。1 回の計測で、ばらつきは見ていない（75〜90 体の間で崩れ始めることは、別の実行 `--counts 1,60,75,90` でも同じだった）。

### 読み取れること

1. **起動は 3〜4 ms、アイドルは 3.1 MB**。暫定値（100 ms、30 MB）を大きく下回る
2. **75 体までは 20 TPS を保つ**。1 tick の平均は 0.16 ms（1 体）〜1.53 ms（75 体）で、tick の 50 ms にはまだ遠い。最大 tick（入室の瞬間を含む）は 35〜46 ms
3. **100 体から、ほぼ全員がサーバーに切られる**。tick の処理は間に合っている（late・skipped が 0）のに、送り先ごとの出力のキュー（`OUTBOX`、256 パケット）が溢れて切られる
   - **観測**（`RUST_LOG=debug` で 100 体を入れたログ）: 100 人が約 0.3 ms の間に一斉に切られた。接続のエラー（`left after an error`）は 0 件。最後の入室の約 0.45 秒後、全員が動き始めてから
   - **計算**: 100 体が 20 回/秒動くと、1 tick に位置と向きの 2 パケット × 99 人 × 100 人分 ≒ 2 万パケットを送る。1 人あたり約 200 パケットで、キューの 256 の 8 割に当たる
   - **推定**: 接続のタスクが 1 パケットごとに flush するため、少し遅れただけで全員のキューが同時に溢れる。→ 書き込みをまとめたら 90 体の切断が 85 → 0 になり、flush の影響は確かめられた（下の「書き込みをまとめたあと」）。ただし 100 体以上はまだ切られる
4. **最初の 1 人で RSS が 3 MB から約 120 MB に増える**。view distance 8 の 289 チャンクの保持と、エンコード済みパケットのキャッシュ（M1-21）が主で、全チャンクが全ブロック光 15 の光データ（1 チャンクで 100 KB 超）を持つ。50 体で約 340 MB、75 体で約 540 MB と、プレイヤーごとにも 4〜5 MB 増える（送信キューと接続のバッファ）

### 見直した暫定値（REQ-PERF-001）

| 項目 | 以前 | いま | 根拠 |
|---|---|---|---|
| アイドル RSS | < 30 MB | < 10 MB | 3.1 MB。ただし最初のプレイヤーで約 120 MB になるので、「プレイヤー 1 人」の値を別に置く |
| 起動からリッスン開始まで | < 100 ms | < 50 ms | 3〜4 ms |
| 20 TPS を保つボットの数 | 500 体 | 500 体（据え置き） | いまは 75 体まで。残りは、配信の絞り込み（REQ-ENT-002）と送信の仕組みの改善で詰める |

### 直す単位（backlog の持ち越し）

- N 体の移動の配信が O(N²)（視界で絞らない）。100 体で出力のキューが溢れる直接の原因
- 1 パケットごとに flush している書き込み（まとめて書けば、同じパケット数でシステムコールが減る）と、`OUTBOX` の大きさ
- 光データが全部 15 のチャンクのメモリ（共有・圧縮できる）と、プレイヤー 1 人あたりのメモリ

## 書き込みをまとめたあと（M1-22、PR #26）

`play::relay` が、キューにたまっているぶんを 1 回の書き込みと 1 回の flush で出すようにした（`Connection::write_frames`）。同じ条件（`--counts 75,90,100,150 --window 8`）の前後で、サーバーが切ったプレイヤーの数:

| bots | 前 | 後 |
|---|---|---|
| 75 | 0 | 0 |
| 90 | 85 | 0 |
| 100 | 18（別の実行では 99） | 10 |
| 150 | 125 | 62 |

- 100 体の前後は実行ごとの揺れが大きい（境目の付近）
- 平均 tick が 1.5 ms → 6〜10 ms に増えたのは、切られずに残るプレイヤーが増え、サーバーが全員に送る仕事をこなしているため。**切られなくなったぶん、O(N²) の送信のコストが見えるようになった**

コミットしない実験として `OUTBOX` を 256 → 1024 にすると、100 体と 150 体で切られなくなった（150 体は平均 tick 22 ms、最大 369 ms、遅れた tick 13）。250 体は崩れた（43 体が失敗し、窓が取れない）。キューの大きさが効くが、最終的な壁は instance スレッドの送信量（視界で絞らない配信）。`OUTBOX` を広げると、遅い接続 1 つが抱える最悪のメモリも増えるので、まだ変えていない。

## 視界で絞ったあと（M1-23）

配信を視界で絞った（[view-culling-plan.md](view-culling-plan.md)）。`xtask bench` に `--layout cluster|spread` と `--view-distance` を足した。散らした 500 体（`--layout spread --view-distance 2`）で、20 TPS・切断 0・1 tick の平均 4.57 ms。全員が同じ場所（cluster）は変わらず、100〜150 体が壁のまま。REQ-PERF-001 の「500 体で 20 TPS」は、散らばった場合に達成し、全員が近い場合は未達。

## 差分と束にしたあと（M1-24）

移動を差分にして 1 tick に 1 回にまとめ、送り先ごとに 1 メッセージの束にし（[move-batch-plan.md](move-batch-plan.md)）、見える人の出現も 1 メッセージにした。全員が同じ場所（cluster）の 500 体で、20 TPS・切断 0・1 tick の平均 28.3 ms（最大 162 ms）。これで REQ-PERF-001 の「500 体で 20 TPS」は、散らばった場合（M1-23）と全員が近い場合の両方で達成した。
